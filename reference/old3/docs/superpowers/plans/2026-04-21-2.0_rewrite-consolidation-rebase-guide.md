## Safety tags

Every branch that pointed into the rewritten range was captured as
`backup/pre-2.0_rewrite-consolidation/<branch>` before the rewrite.
List them with:

```
git tag -l 'backup/pre-2.0_rewrite-consolidation/*'
```

These tags are the escape hatch: if any rebase goes badly, reset the
branch back to its backup tag. Delete the tags only once every worktree
has been successfully rebased.

Additional tags from the earlier reimplement-resource-classes
consolidation (kept for reference, safe to delete):

- `backup/reimplement-resource-classes-pre-consolidation` →
  `240307d19` (the unconsolidated 28-commit tip of
  reimplement-resource-classes before the first pass).

## Rebase recipes

Two groups of branches, two rebase commands.

### Group A — branches previously based on old `2.0_rewrite` tip (`95a6441a7`)

These branches had the 6 rewritten commits in their ancestry. They
include every `plan-stage-*`, `history-consolidation`, and
`reimplement-resource-classes`. Rebase with:

```
git checkout <branch>
git rebase --onto 2.0_rewrite backup/pre-2.0_rewrite-consolidation/2.0_rewrite
```

`reimplement-resource-classes` is a special case: its 9 consolidated
commits are already in the new `2.0_rewrite`, so the simplest cleanup
is to fast-forward-reset it instead of rebasing:

```
git checkout reimplement-resource-classes
git reset --hard 2.0_rewrite    # tree is already identical
```

The backup tag is still there if anything looks off.

## After every branch is rebased

Once all worktrees check out cleanly on top of the new `2.0_rewrite`:

```
git tag -l 'backup/pre-2.0_rewrite-consolidation/*' | xargs -r git tag -d
git tag -d backup/reimplement-resource-classes-pre-consolidation
```

And push `2.0_rewrite` force-with-lease. No branches except
`2.0_rewrite` need to be force-pushed; the rebased worktree branches
will have new SHAs and should be pushed as normal (or force-pushed if
they were already published).
